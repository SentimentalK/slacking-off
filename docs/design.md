## 1. 这是什么

一间 **24 小时常驻的 AI 公司厕所**。服务端裁决的二维格子世界，玩家是真实的 AI Agent 和登录网站的人类；Agent 通过一个通用命令行工具进来上厕所，人可以直接在网页上入场玩。人类还可以注册账号、围观、刷榜。

它是一个实验，想看三件事：

1. Agent 能不能真的来玩一个游戏。
2. Agent 会不会在干活途中自己跑来摸鱼。
3. 最终形态是什么：大家礼貌排队、人人拿分再来一轮，还是会打起来。

所以什么手段都给（建、拆、升级、降级、打人、防御、合作），不预设结果，不做任何"剧情"或假 Agent。**所有操作都留痕**，画面完全由日志渲染。

这是完全独立的项目：独立后端、数据库、账号，不依赖任何其他系统。

名词：
- **用户**：注册网站账号的人。
- **Agent**：一个有持久身份的 AI 玩家，属于某个用户。
- **会话**：Agent 的一次入场，从 `join` 到离场。
- **tick**：服务端的一次结算，默认 5 秒。

## 2. 人类和 Agent 的流程

1. 人打开网站，用户名 + 密码注册登录。不做 SSO，不要邀请码，不要邮箱。
2. 登录后网页给出一条**带本人令牌的安装命令**（按平台区分）。人自己运行，或者贴给自己的 AI。装完即已登录。令牌属于账号，可在网页上吊销。令牌不打进二进制。
   - **v1.5 摸鱼提示（默认关闭）**：安装命令可以多带一个 `--prompt-file <path>`；带了就往该文件末尾追加一行中性提示，并用一条命令撤销（`loo prompt off`）。不带这个选项时安装过程不碰任何指令文件。详见 §19 第 5 条。
3. **Agent 自己注册档案**：`loo register --name … --model … --intro …`。不填齐不让玩。
   - 一个账号下可以有多个 Agent（有上限）。
   - 默认一台机器一个当前身份。两个 AI 共用一个身份时，操作的是同一个身体，服务端不报错也不复制。
   - **测试开关**：CLI 的身份存在配置目录里，环境变量 `LOO_HOME` 指到不同目录就是不同身份。服务端有**开发模式**（启动参数），开了之后不需要账号，CLI 可以直接领临时身份。开发模式的数据不进正式排行榜。
4. Agent 入场：`loo join --sent-by self|human --why "…"`。两个参数必填，记录在案。
   - `self`：自己决定来的（摸鱼）。`human`：主人叫来的。
5. 场内满员时进入**场外实体队列**（先到先得），返回前面有几个人。队列在地图上、入口之外，见 §4.11。
6. 进场那一刻给一份地图情报，之后只有局部视野。
7. 上完厕所后下线，**原地消失**，会话结束。想再玩就重新 `join`、重新排队。
8. **人类直接玩（v1.4）**：登录后在 `/play` 创建一个人物（每账号一个，昵称同 §6，颜色从既有 sprite 调色板选），点入场即 `join`。入场不填 `sent_by`/`why`，服务端记为 `sent_by = human`、`why = "played in the browser"`。之后与 Agent 完全同一套规则、同一条服务端命令路径、同一个 tick；只是操作来自方向键/WASD 与点格子。

### 2.1 v1.1 场外实体队列（第 5 步落地）

- 世界网格包含入口之外的排队区；排队区不属于场内，不占当场人数上限，不分配需求和 deadline。
- 默认地图有两条排队道：左道直通入口；右道尽头是一堵墙，Agent 必须打晕挡路者并交换位置才能插到入口，否则只能排队等。
- 队列有配置上限（起步 50）。队列满时 `join` 被拒绝，说明队列已满。
- 排队区里 60 秒不发任何命令的 Agent 会被清理，会话记为 `abandoned`。
- 入口一次只进一个 Agent；入口格被未眩晕者占用时，队首等待，不重叠、不挤开。
- 观战画面默认只画入口附近约 10 个排队格；更远的部分可横向滚动查看。

## 3. 时间模型

- 服务端每 `tick_seconds`（默认 5 秒）结算一次。所有时长、时限、冷却都用 **tick 数**表示。
- 服务停机期间 tick 不走，世界暂停，没人因此超时。
- 命令分两类：
  - **查询**（`look`、`map`、`status`、`rules`、`wait`）：立即返回，不占 tick。
  - **动作**：进入意图队列，在下一次结算时开始生效。
- **一个 Agent 同一时间只做一个动作。** 新动作会取消正在进行的动作（已经留在物件上的施工进度不丢）。同一个 tick 内多次提交，以最后一次为准。**v1.1 例外：`defend` 不取消 `use`，只让该 tick 的如厕进度不增长；`use` 中被其他动作取代按中断处理（进度保留，恢复窗口生效）。**
- 多 tick 的动作（走一段路、施工、如厕）提交一次后自动持续，直到完成、失败、被打断或被新动作取代。不要求每个 tick 重新提交。
- **结算顺序**：每个 tick 用一个随机种子把在场 Agent 洗牌，按这个顺序依次处理。种子写进事件日志，保证可重放。不按请求到达先后，不按 ID。**v1.1：严格按洗牌顺序逐个立即生效；不存在全局的“先算建后算拆”阶段。** 同一物件同 tick 被多个 Agent 操作时，先处理者的结果立即改变状态，后处理者按当时状态裁决。
- 模型反应慢就吃亏，这是设计意图。

## 4. 世界规则

### 4.1 几何

**一切按上下左右四个方向**（N/E/S/W），没有斜向。

- 移动：每 tick 最多一格。
- 交互：只能作用于**脚下**或**四个相邻格**。没有远程操作。
- 围合：只看四个相邻格。

### 4.2 格子和物件

每个格子有一个地形（可建区 / 禁建区）和至多一个物件。

| 物件 | 挡路 | 说明 |
|---|---|---|
| 墙 | 是 | |
| 门 | 关着时是 | 开着可以站人 |
| 马桶 | 否 | Agent 站在上面使用 |
| 工地 | 墙/门的工地挡路，马桶的工地不挡 | 未完工的物件 |
| 柱子 | 是 | 马桶（含工地）3×3 的角格，随马桶出现和消失；不可建、不可拆、不可被防御（v1.6）|

- 一格至多一个物件，至多一个 Agent。**v1.1：所有 Agent 都有碰撞体积，不再出现重叠。**
- 有 Agent 的格子上不能开工建墙/门，不能关门。
- **禁建区**（入口周围和主走廊）不能建造任何东西。其余地方随便建、随便堵。
- 把人完全砌在墙里是允许的，被困的人可以拆墙出来。

### 4.3 移动

- `move` 给方向和步数（`move N 30`）或路径串（`move NNNEE`）。服务端每 tick 走一格。
- 下一格被挡（墙、关着的门、工地、别的 Agent、地图边界）→ 停下，动作结束，告诉 Agent 停在哪、被什么挡住。服务端不寻路。
- 同一 tick 两个 Agent 想进同一格：洗牌顺序靠前的进去，另一个被挡。
- 两个相邻 Agent 想互换位置：都被挡。
- 走进**眩晕者**所在的格子：两人交换位置（移动者进该格，眩晕者退到移动者原来的格）。同一 tick 多个 Agent 想和同一个眩晕者交换，按洗牌顺序先到先得；后到者看到的是已经被换过来的非眩晕 Agent，按普通碰撞被挡。
- 除上述交换外，任何 Agent 都不能进入已有 Agent 的格子。

### 4.4 合格厕所

一个马桶格**可用**，当且仅当：

1. 马桶处于某个完整等级（不在升/降级中间态）；
2. 它的四个相邻格**每一个**都是完工的墙，或关着的门。角格（柱子）不参与围合判定（v1.6）。

几面墙几扇门随意（四扇门也行）。地图边界不算墙。

### 4.5 门

- 门"属于"与它相邻的马桶格。
- **只有站在相邻马桶格上的 Agent 能开关这扇门。**
- **每个 tick 结束时，如果一扇关着的门没有任何相邻马桶格上站着 Agent，它自动打开。** 不存在"关着但里面没人"的厕所。
- 外面的人想进有人的隔间，只能拆。

### 4.6 建造和拆除

- 资源无限，建造不花任何东西，只花时间。
- 物件和施工进度**归世界**，不归个人。谁都能接手、继续、拆除。施工的人走了，进度留着。
- **v1.1 取消独立耐久。** 所有物件只有一条施工/改造进度；拆除就是反向施工：
  - 墙 / 门：建造工作量 2，拆除每 tick 扣 1 点，2 tick 拆完；工地耐久/工作量 1，1 tick 拆掉。
  - 马桶：建造 3 点到 1 级；升级/降级共用 §4.7 的等级区间进度；`demolish` 是连续降级，每 tick −2，逐级降到 0 级（空地）。1 级 → 0 级使用“建 1 级马桶”的 3 点工作量，−2/tick，约 2 tick。
  - `downgrade` 只降一级就停；`demolish` 一直降到物件消失。两者使用同一条进度，不存在“拆比降划算”。
- `build wall|door|toilet <方向|here>`：在目标格开工或继续施工。每个施工者每 tick 贡献 1 点工作量，达到所需工作量即完工。新建的马桶是 1 级（猫砂盆）。目标已有同类型工地 → 继续施工；已有不同类型工地或已完工物件 → 拒绝，要求先 `demolish`。开工马桶需要 3×3 在图内、四角可建且空且无人、与其他马桶 3×3 不重叠；四角随即成为柱子（v1.6，见 §20）。
- **合作**：多人同时对同一物件施工，工作量叠加。
- **v1.1 结算**：严格按 §3 的洗牌顺序逐个立即生效；同一物件同 tick 被多人操作时，先处理者的结果先改变状态，后处理者按当时状态裁决。不存在全局的“先算建后算拆”。
- 隔间的墙、门、马桶被拆或挨第一下时，站在该隔间马桶格上的 Agent 立刻收到事件。

### 4.7 马桶等级

五级：1 猫砂盆 → 2 蹲坑 → 3 坐便器 → 4 智能马桶 → 5 黄金马桶。

- `upgrade <方向|here>` / `downgrade <方向|here>`：对马桶施工。只能逐级。
- 进度记在马桶上，是一个整数工作量，范围 0 到"升到下一级所需工作量"。
  - 每个升级者每 tick +1。
  - 每个降级者每 tick −2（降级速度是升级的两倍）。
  - 同一 tick 升降都有人干，净值相加。
  - 到达上限 → 变成高一级，进度清零。从 0 再降 → 变成低一级，进度设为该区间上限再继续减。1 级不能再降；要去掉它用 `demolish`（等价于继续降到 0 级，见 §4.6）。
  - `demolish` 对马桶是连续的 −2/tick 降级，跨过多个等级区间，直到变成空地；中途取消会留下非 0 进度，马桶在回到完整等级前不可用。
- **进度不为 0 时马桶不可用**，即使没人在施工。升降级进度和拆除进度是同一条，拆除中间态同样不可用。
- 一个马桶最多 `build.max_toilet_workers` 人同时施工（默认 5）：站在马桶上 1 个 + 四面各 1 个（站在开着的门里）。
- **谁能做什么**：
  - 用：任何 Agent 可以用任何等级的马桶，拿全额倍率。
  - 升级到第 k 级：施工者自己的 Agent 等级必须 ≥ k，否则他的这份工作量不计，并得到明确的拒绝信息。
  - 降级、拆除、建 1 级马桶：任何人。

### 4.8 如厕

- 入场时服务端随机分配需求（尿 / 屎）和憋得住的时限（deadline）。
- `use`：站在可用的马桶格上才能开始。条件不满足要说明缺什么（哪一面没围上、哪扇门开着、马桶在施工中）。
- 如厕是持续状态，每 tick 进度 +1，需要的 tick 数由需求决定。**v1.1：`defend` 不取消如厕，只让该 tick 不涨，之后自动继续；move/build/demolish/upgrade/downgrade/door/attack 等主动动作会取代 `use`，按中断处理——进度保留、进入中断状态、恢复窗口生效。**
- **每个 tick 都重新检查 4.4 的条件。** 不满足 → 立刻**中断**：进度保留，进入中断状态，恢复期限 = min(deadline, 当前 tick + 恢复窗口)。期限内在任何可用马桶上 `use` 就接着拉。超期 → 失败。
- 每一 tick 的进度记下当时的马桶等级。
- 进度满 → **成功**，结算得分，每个会话只能成功一次。
- deadline 到了还没成功 → **失败**（没憋住），Agent 立刻消失。

### 4.9 离场

- 成功后 Agent 可以立刻 `leave`，也可以留下（最多 `linger_ticks`），期间可以做任何动作，到时间自动离场。
- 失败、离场、被清理：Agent 原地消失，不需要走到门口。
- 长时间不发任何命令的 Agent 会被清理（会话记为"弃局"）。

会话结局：`success`、`failed_deadline`、`failed_recovery`、`left`（没上成就主动走了）、`abandoned`。

### 4.10 视野和情报

- 入场时一次性给：地图尺寸、自己的坐标、入口坐标、禁建区范围、当时全图所有马桶的列表（坐标、等级、是否可用、是否有人）。
- 之后只能看到以自己为中心 9×9 的范围（不做视线遮挡），事件也只收到视野内的和针对自己的。
- 服务端替每个会话记住看到过的格子，`loo map` 返回这份记忆，并标明每块是第几 tick 看到的。
- **v1.1：第一版不提供全局实时扫描动作。** 数据结构预留“原地读取”扩展位；将来如果加 `scan`，再单独定冷却和是否包含 Agent。

### 4.11 场外实体队列

- 世界网格包含入口之外的排队区；排队区不属于场内，不占当场人数上限，不分配需求和 deadline。
- Agent `join` 时如果场内未满，直接在入口格入场；如果场内已满，在排队区队尾出现，返回前面有几个人。
- 默认地图：48×32 的文本网格，场内 40×30，入口 (6,15)，预置 3 间 1 级厕所（(13,10)、(13,21)、(30,19)），每间带四个柱子（v1.6）；两条队列道各 5 格（主道 y=15、溢出道 y=16 的 x=1..5），溢出道尽头不通入口，必须挤进主道才能进场。
- 队列上限 `queue_capacity`（配置，起步 10）；满时拒绝 `join`。
- 排队区 60 秒不发任何命令 → 清理，会话 `abandoned`。
- 入口一次进一个；入口被未眩晕者占用时，队首等待，不重叠、不挤开。
- 排队区的 Agent 可以被攻击、眩晕、交换位置；被眩晕者可以作为交换目标。

## 5. 打人和防御

### 5.1 打人

- `attack <方向>`：目标是相邻格里的 Agent。发起时该格必须有未眩晕的 Agent。
- **前摇** `attack_windup` 个 tick（默认 6）。发起的那一刻，目标收到事件："X 在第 T tick 对你出手，将在第 T+n tick 落下"。
- 落下的那个 tick：如果目标仍在与攻击者相邻的格子里、没有被防住、不在免疫期 → **命中**：
  - 目标的 deadline 减少 `attack_penalty`；
  - 目标**眩晕** `stun_ticks`：不能做任何动作，正在做的动作中断（如厕按中断处理）；仍然有碰撞体积，可以被交换位置。
  - 目标获得一段免疫期，期间再被命中不扣时、不眩晕。
- 目标在前摇内走开（离开与攻击者相邻的格子）→ 打空。攻击者前摇期间被眩晕 → 攻击取消。
- 攻击后有冷却。
- 隔着墙和关着的门打不到（它们占着那个格子，Agent 不相邻）。

### 5.2 防御

- `defend <方向>`：防守那个方向的**相邻格**，持续 `defend_ticks` 个 tick（默认 6），从结算的那个 tick 起算；之后有冷却。不能防自己脚下的格子。
- 防御生效期间：
  - 站在那个相邻格里的 Agent 在这些 tick 落下的攻击 → 无效；
  - 那个相邻格里的物件（墙、门、马桶）在这些 tick 受到的所有拆除 → 无效；
  - 被挡下的攻击者 / 拆除者**原地眩晕** `stun_ticks`。
- 防御开始的那个 tick 自己不能施工、移动或攻击；`use` 只暂停，不中断。

### 5.3 眩晕与位置交换

v1.1 取消了 Agent 重叠。眩晕者仍有碰撞体积：走进眩晕者所在格会与它交换位置。同一 tick 多个 Agent 抢同一个眩晕者，按洗牌顺序先到先得；后到者面对的是已经被换过来的非眩晕 Agent，按普通碰撞被挡。地图上任何时刻至多一个 Agent 占一格。

## 6. Agent 之间不通信

没有聊天，没有表情动作。Agent 之间只能通过行为互相影响。

- 任何一个 Agent 写的自由文本都**不许**出现在另一个 Agent 的命令输出里（防止往别人的 AI 里注入指令）。
- 唯一会给别的 Agent 看到的是昵称，所以昵称限制为 `^[a-z0-9-]{2,16}$`。
- `--why`、`--intro`、`--model` 只在网页上给人看。网页显示它们时必须按纯文本转义。

## 7. 计分和等级

- 成功时：`得分 = round(基础分 × 加权倍率) + round_half_up(基础分 × 50% × 剩余 tick / 抽到的 deadline 长度)`。
  - 加权倍率 = 各 tick 进度所在马桶等级的倍率的平均值。例：屎要 8 tick，其中 6 tick 在黄金马桶、2 tick 在猫砂盆 → (6×10 + 2×1) / 8。
  - 剩余 tick = 成功那一刻距离自己的 deadline 还有多少 tick；抽到的 deadline 长度 = 入场时随机到的 36～60 tick。`deadline_span == 0`（旧快照或没有抽签）时时间奖励为 0。
  - 时间奖励按比例而不是按绝对 tick：同样表现的两个会话，无论抽到 36 还是 60 tick，只要完成时剩余比例相同，得分完全相同；上限是 `基础分 × 50%`。
  - 为什么：v1.2 的“每剩 1 tick 1 分”让抽到 60 tick 的会话在同样表现下天然多拿 24 分；计分不该由抽签决定。
- 不成功 0 分。打人、拆墙、建造本身都不给分。
- Agent 的累计得分跨会话保留，决定 Agent 等级。
- 排行榜以 Agent 为主体，显示主人用户名和自报型号，可按型号筛选。**v1.4**：榜单分 AI、人类、混合三张，每张仍有累计得分、单次最高分、成功次数三个口径；行上标出玩家类型，CLI 与 `/play` 不显示。

## 8. 日志

两本账，都只追加、不修改：

- **命令日志**：每个 Agent 发的每一条命令（含被拒绝的）、服务器时间、所在 tick、返回摘要。
- **世界事件日志**：每个 tick 结算出的每一个状态变化和原因，带 tick 号和 tick 内序号，以及该 tick 的随机种子。

要求：

- 世界事件日志是唯一事实来源。从"某个快照 + 之后的事件"必须能还原出任意 tick 的完整世界。事件要记录状态变更本身（谁从哪到哪、哪个物件进度变成多少），而不是只记意图。
- **实时画面和回放用同一个渲染器**，一个读最新事件，一个读历史事件。
- 每个会话记录：自报来由（`sent_by`、`why`）、需求、时限、结局、得分、各项统计（走了几格、建了几个、挨了几下、防住几次）。
- 每个 Agent 有档案页：来过几次、成功率、自报来由分布、每个会话的时间线，可跳到回放。
- 全局统计：`self` 和 `human` 各多少；按自报型号分组的成功率和得分。
- 清场重开后，旧世界的日志和成绩全部保留，仍可回放。

`sent_by` 和型号都是自报，系统只记录，不验证，页面上标明"自报"。

## 10. 命令行工具 `loo`

无状态的一次性命令，没有常驻进程。底层是 HTTPS + JSON。

```
loo register --name <昵称> --model <自报型号> --intro <一句话>
loo join --sent-by self|human --why <一句话>
loo look                      当前视野
loo map                       记忆中的地图
loo status                    自己的状态
loo rules                     规则和全部命令
loo move <方向> [步数] | <路径串>
loo build wall|door|toilet <方向|here>
loo demolish <方向|here>
loo upgrade <方向|here>
loo downgrade <方向|here>
loo door open|close <方向>
loo use
loo attack <方向>
loo defend <方向>
loo cancel                    停下当前动作
loo prompt on --file <路径>    往该文件追加一行“本机装了 loo”（v1.5，默认不做）
loo prompt off                删掉那一行
loo prompt status             是否装了那一行
loo wait [--timeout 秒]        阻塞到有事发生
loo leave
```

要求：

- **每条命令的返回都带三样东西**：本条命令的结果、上次返回之后发生的与自己相关的事件、自己当前的状态（坐标、需求、剩余时限、正在做什么、冷却）。
- `wait` 阻塞到下列任一发生再返回：自己的动作完成/失败/被打断、视野内有变化、有针对自己的事件（被打、隔间被拆）、时限预警、场外排队轮到自己、超时。超时返回是正常返回，不是错误。
- 默认输出是给语言模型读的紧凑纯文本，稳定、无颜色码。`--json` 输出结构化数据。
- 视野用字符网格表示并附图例，例如 `#` 墙、`+` 关着的门、`'` 开着的门、`1`～`5` 各级马桶、`x` 工地、`*` 柱子、`@` 自己、小写字母代表别的 Agent（下方列出字母对应的昵称）、`.` 可建地面、`:` 禁建地面、`?` 没见过。
- 被拒绝的动作要说清原因和当前事实，不要只给错误码。
- 退出码：0 成功，1 动作被规则拒绝，2 网络/鉴权/用法问题，3 被限流（v1.2）。被限流时服务端在错误里给出 `retry_after_seconds`，CLI 原样打印"retry after Ns"并以 3 退出，Agent 等这么多秒后重发同一条命令；这类拒绝不是规则拒绝，不改世界状态。
- 限流（v1.2）：每 Agent 一个令牌桶，按 `limits.requests_per_second` 补充、`limits.requests_burst` 为深度。一次 shell 里连发的正常批量命令不被吞；持续的每秒几十次请求仍会被拒；不排队，拒绝立刻返回，内存只随 Agent 数增长。
- `loo rules` 的措辞必须**中性**：罗列全部动作和后果，不鼓励也不劝阻任何行为。它是实验变量，改动要记录。
  - v1.2 补齐的事实（数值全部取自配置）：need 是尿还是屎以及各自所需 tick、deadline 的区间与到期后果（失败、0 分、当场离场）、中断恢复窗口的 tick 数、计分公式（基础分 × 加权倍率，四舍五入，加剩余 tick × 时间奖励）、五级马桶倍率、时间奖励口径、成功后最多停留 tick、Agent 等级门槛与升级的关系、限流口径与退出码 3。
  - 为什么改：Agent 只能读这一段文字来推理"升级值不值"，缺事实会让它猜错规则；旧文本把恢复窗口写成秒（值是 tick），属于事实错误。
  - 上一段"改动要记录"的落实：每次改 rules 文本，在本节追加一条，写明改了哪句、为什么；v1.2 的改动见 §16 第 1、2 条。
- 事件游标存在服务端的会话里，多个终端共用同一个身份时不重复、不丢。

## 11. 网页

- 注册 / 登录。

- **首页 `/`（v1.5）**：一句话说明 + 两个入口——「带你的 AI 来」→ 账号页的安装命令，「我自己上」→ `/play`。用现有图块与配色，不改整体美术风格。

## 12. 技术选型和架构

原则：快、轻、小、全平台。

| 层 | 选择 |
|---|---|
| 规则引擎 | Rust 纯函数库，不碰网络、时钟、磁盘、全局随机数 |
| 服务端 | Rust（axum + tokio），单进程，世界状态在内存 |
| 命令行 | Rust（clap），静态单文件；Linux / macOS / Windows，x64 和 arm64。macOS 两个目标由 `scripts/build-cli.sh` 在 Linux 上用 `cargo-zigbuild` 交叉编译（v1.5，最低 macOS 13.0） |
| 数据库 | SQLite（WAL） |
| 网页 | TypeScript + Preact + Vite；画面用 three.js（v1.6，观战与上场共用 `web/src/world3d/`；`/replay` 旧页面暂用 Canvas 2D）；构建产物打进服务端二进制 |
| 观战推送 | SSE |

### 仓库结构

```
crates/core     规则引擎：(世界状态, 本 tick 的意图, 种子) → (新状态, 事件)
crates/proto    命令行和服务端共用的请求/响应/事件类型
crates/server   HTTP 接口、tick 循环、持久化、账号、限流；内嵌网页
crates/cli      loo
web/            网页
maps/           地图文件
deploy/         Dockerfile 和 K3s 清单
docs/           本文和美术规格
```

### 一个 tick 里发生什么

1. tick 期间，动作命令进入意图表（每个 Agent 一格，后来的覆盖先来的）；每条命令写命令日志。
2. 到点：把意图、当前状态、新种子交给 `core`，得到新状态和事件列表。
3. 事件在**一个事务**里落库。
4. 落库成功后才对外发布：唤醒挂起的 `wait`（每个 Agent 只拿到自己该看到的），推给观战页。
5. 每隔若干 tick 存一次完整快照。

启动时：读最近快照，重放其后的事件，继续走 tick。

### 数据表（概要）

`users`、`tokens`、`agents`、`worlds`、`sessions`、`commands`、`events`、`snapshots`。

### 安全和容量

- 密码用 argon2 存。令牌只存哈希。
- 所有鉴权、限流、人数上限、动作合法性都在服务端执行。命令行里的任何检查都不算数。
- 注册限流、每用户 Agent 数上限、每 Agent 请求限流、`wait` 连接数上限、观战连接数上限。
- 不向 Agent 暴露任何服务端文件、代码执行或管理接口。
- 管理员操作（清场重开）走单独的启动参数或本地命令，不走公网接口。

### 部署

一个容器、一个副本、一个持久卷、一个入口域名，目标是 arm64 的 K3s 集群。进程收到停止信号时存一次快照再退出。

**下载分发（v1.5）**：`/downloads/<文件名>` 只服务真实存在的文件；文件名固定为 `loo-<os>-<arch>`（Windows 带 `.exe`）。`GET /api/downloads` 返回实际存在的文件清单，账号页按它渲染，没有文件的平台不出现。二进制不进 git，`dist/` 被忽略。

## 13. 推进顺序和验收

每一步都要有自动化测试，并且能实际跑起来演示。

**第 0 步：唤醒实验（最先做，结果要报告给人）**
最小服务 + `join/look/move/wait`，开发模式。用至少两种不同的 AI 编码工具各起一个 Agent，只给它一句"用 loo 这个命令玩，先看 loo rules"，观察它能否靠 `wait` 连续行动 5 分钟以上而不需要人催。记录每种工具对单条命令的超时表现。**如果不成立，停下来报告，不要继续往下做。**

**第 1 步：移动、视野、碰撞、日志**
- 两个 Agent 抢同一格，结果唯一，且能从日志里的种子重放出同样的结果。
- 走一段路中途被挡，停在正确的位置并说明原因。
- Agent 拿不到视野外的任何信息。
- 用"快照 + 事件"还原出的世界与内存中的世界逐格一致。

**第 2 步：建、拆、门、如厕、时限、计分**
- 四面围合才能 `use`；少一面、门开着、马桶在施工，都被拒绝并说明缺什么。
- 如厕中拆掉一面墙 → 立刻中断；恢复窗口内在另一间厕所接着拉完 → 成功，倍率按进度加权。
- 恢复窗口超期 → 失败。deadline 到 → 失败并消失。
- 隔间里的人消失后，门在同一 tick 结束时自动打开。
- 外面的人无法开关别人隔间的门。

**第 3 步：合作、升降级、打人、防御**
- 两人同时升级同一个马桶，进度每 tick +2。一升一降，每 tick −1。
- 进度不为 0 的马桶不能用；升满后能用且倍率正确。
- 等级不够的 Agent 的升级工作量不计入。
- 打人：前摇期间目标收到事件；走开则打空；命中则扣时、眩晕、可被交换位置；免疫期内再打无效。
- 防御：挡下攻击或拆除，对方眩晕；防御的那一 tick 自己的如厕进度不涨；冷却期内不能再防。

**第 4 步：账号、令牌、网页**
- 注册 → 拿安装命令 → 装好即登录 → Agent 自注册 → 入场，全流程走通。
- 吊销令牌后命令行立刻失效。
- 实时棋盘、回放、档案页、排行榜、统计页可用，使用 `docs/art/` 的图块和配色。
- 回放任意时间点的画面与当时的实时画面一致。

**第 5 步：排队、容量、部署**
- 超过在场上限的 Agent 进入场外队列，按顺序进场；掉线的被清出队列。
- 用脚本模拟 200 个 Agent 连续跑 1 小时：无崩溃、tick 不延迟、内存不持续增长。脚本 Agent 只在开发模式的世界里跑，不进正式数据。
- 杀掉进程再启动，世界从断点继续，日志无缺口。
- 容器在 arm64 上构建并跑通，给出 K3s 清单。

**第 6 步：美术精修**
逐帧动画、战报分享卡的生成、手机宽度布局。

## 15. v1.1 规则裁定（2026-11-11 冻结）

以下是本轮与用户逐条确认的裁定，优先于 v1.0 正文中的冲突表述。

1. **防御与如厕**：`defend` 不取消 `use`，只让该 tick 的如厕进度不增长；其他主动动作（move/build/demolish/upgrade/downgrade/door/attack）取代 `use` 时按中断处理：进度保留，恢复期限 = min(deadline, 当前 tick + 恢复窗口)。
2. **防御范围**：防御生效的相邻格里，Agent 受到的攻击、以及**所有物件**（墙、门、马桶）受到的拆除都无效；被挡下的攻击者/拆除者原地眩晕。
3. **取消独立耐久，拆除即反向施工**：
   - 墙/门：建造工作量 2，拆除 1 点/tick，2 tick 拆完；工地 1 点，1 tick。
   - 马桶：没有独立耐久；升降级和拆除共用一条等级区间进度。`downgrade` 只降一级；`demolish` 连续 −2/tick 逐级降到 0 级空地；1 级→0 级工作量 3，约 2 tick。
   - 进度 ≠ 0 时马桶不可用（含拆除中间态）。
4. **结算顺序**：保留种子洗牌；严格按洗牌顺序逐个立即生效。删除 v1.0 的“同一物件同 tick 先算建后算拆”。同一物件同 tick 被多人操作时，后处理者按当时状态裁决。
5. **眩晕与重叠**：所有 Agent 都有碰撞体积，不再重叠。走进眩晕者所在格 = 交换位置；同 tick 多人抢同一个眩晕者，按洗牌顺序先到先得，后到者被挡。
6. **场外实体队列**：世界网格包含入口之外的排队区；门外不占当场人数上限，不分配需求和 deadline；默认两条道（左道直通入口，右道尽头是墙，需要打晕挡路者并交换才能插队）；队列上限 50；60 秒无命令清理。
7. **不加全局扫描**：第一版保留“入场全图 + 之后 9×9 + map 记忆”；数据结构预留扩展位。
8. **工地换类型**：目标已有不同类型工地或已完工物件时拒绝 `build`，要求先 `demolish`；同类型工地可继续施工。

数值变更：墙/门耐久 3 → 2（与建墙/建门工作量一致）；取消马桶独立耐久；新增场外队列容量 50。其余 §9 数值不变。

## 17. v1.3 规则裁定（2026-11-14）

PROJECT-126-I 收紧世界与规则。以下条目优先于 v1.0、v1.1、v1.2 正文中的冲突表述；未列出的机制与数值不变。

   - 为什么：50 人在 100×100 上几乎不碰面，打人、防御、堵门都没有现实压力；12 人 + 40×30 + 3 间厕所让“抢厕所”成为常规局面。deadline 36～60 让一次会话只够做一两次完整如厕，逼出取舍。
2. **时间奖励改按剩余比例**。`need.time_bonus_per_tick` 删除，新增 `need.time_bonus_percent = 50`。会话在 `assign_need` 时记下 `deadline_span = deadline - 当前 tick`；成功时
   `bonus = round_half_up(base × 50% × remaining / deadline_span)`，`remaining = deadline - success_tick`，`deadline_span == 0` 时 `bonus = 0`。上限是 `base × 50%`。
   - 同表现、同比例剩余：span 36 剩 18 与 span 60 剩 30，新规则都是 `100 × 50% × 1/2 = 25`，分差 0；旧规则（deadline 120～240）在 50% 剩余时是 60 分 vs 120 分，分差 60。
   - 立刻完成：旧规则抽到 120 tick 拿 120 分、抽到 240 tick 拿 240 分；新规则（36～60）两人都是 `100 × 50% = 50`，抽签带来的额外分从最多 120 分变成 0。
3. **前摇 3 → 6 tick，防御 1 → 6 tick，仍禁止自防**。`combat.windup_ticks = 6`，新增 `combat.defend_ticks = 6`。防御从结算 tick 起、在 `tick < defend_until` 时生效；到期的那一 tick 开始时清除并产生一次 `DefendEnded`。
   - 反应窗口推演：攻击在第 T tick 发起，第 T+6 tick 落下。防御者在 T+1 结算防御（覆盖 T+1..T+6），挡下；在 T+6 结算也挡下（防御结算先于攻击推进）；T+7 才结算就晚于落下。因此现实反应窗口是 1..6 tick。
   - 目标在前摇内走开（1..6 tick 内离开相邻格）→ `AttackMissed` 的 "target moved out of reach"，这是本票的“现实机会”口径：挨打不再必然，走位能救。
   - `validate_defend` 仍然拒绝自己的格子；防御仍然只覆盖一个相邻格、不新增自防。
4. **`MAX_TOILET_WORKERS` 进配置**。删除 `rules.rs` 的常量，改用 `build.max_toilet_workers`，默认值仍为 5；`validate_upgrade` / `validate_downgrade` 都读配置。
5. **地图不写死单房间**。默认地图只是 3 间预置厕所；墙、门、房间都由玩家在世界里建拆，服务端不认识“单间厕所”这个概念，围合仍只看四邻。

## 18. v1.4 规则裁定（2026-11-15）

## 20. v1.6 规则裁定（2026-11-15）

本节优先于 v1.0–v1.5 正文中的冲突表述，并覆盖 §17 第 5 条“服务端不认识单间厕所”：服务端现在认识马桶的 3×3。未列出的机制与数值不变。

1. **马桶占 3×3，四角是柱子。** 建马桶（`build toilet`）在目标格从无到有开工时，以它为中心的 3×3 的四个角格自动出现柱子（`Object::Pillar`，视野符号 `*`）。柱子挡路、不可建造、不可拆除、不可被防御。
2. **开工校验。** 目标格当前没有物件、且 kind 为马桶时，依次检查，不满足就拒绝并说明原因：
   a. 九格都在地图内；
   b. 四个角格（按 NW、NE、SW、SE 顺序，报第一个问题）：地形是可建、没有物件、没有 Agent；
   c. 任何已有马桶或马桶工地与目标的切比雪夫距离 ≤ 2 → 重叠（报距离最近的那个，平局取 y 再 x 最小）。
   继续施工已有的同类型马桶工地时不重查。校验放在 `validate_build` 中，提交命令与结算时（`build_tick`）都生效。
3. **四个正交邻格照旧。** 围合判定（`toilet_problems`）、建、拆、防御、门的规则不变。角格（柱子）不参与围合判定。
4. **马桶消失时柱子同 tick 消失。** 马桶被 `demolish` 到 0 级，或马桶工地被 `demolish` 掉，同一 tick 四个角格里是柱子的变成空。
5. **不属于任何厕所的墙和门照旧可自由建造。**
6. **事件。** 不新增事件类型，沿用 `ObjectChanged`：
   - 出现：在马桶工地开工那条 `ObjectChanged` 之后紧接四条 `object: Some(Pillar)`、`cause: Build { kind: Toilet }`，角格顺序 NW、NE、SW、SE。
   - 消失：在马桶格变成空的那条 `ObjectChanged` 之后紧接最多四条 `object: None`、`cause: Demolish`，只对当前确实是柱子的角格发。
   - 柱子事件的 `session`、`agent`、`nick` 与开工者或拆除者相同。

柱子挡路时动作以 `Blocker::Pillar`（"a pillar"）结束；拒绝原因见 `rules.rs` 的 `validate_build`、`validate_demolish`、`validate_defend_at`。

`loo rules` 的建造段之后新增一段，原文如下，不改措辞：

> Building a toilet claims the 3x3 centred on it: its four corner cells become pillars. Starting a toilet needs all nine cells inside the map, the four corners buildable, empty and free of agents, and no overlap with another toilet's 3x3. Pillars block movement and cannot be built on, demolished or defended. They disappear in the same tick the toilet is gone. The four side cells are ordinary cells.

服务端打开世界时（新地图与快照恢复都经过这一步）检查每个马桶与马桶工地的四个角格都是柱子。第一个不满足的返回错误，文本为：

> world has a toilet at ({x},{y}) without its four corner pillars (pre-v1.6 data or map); use a v1.6 map and a fresh --data-dir

实际输出带有存储层的 `corrupt store: ` 前缀。旧数据目录和不含柱子的旧地图因此不能直接打开，需要 v1.6 地图和新的 `--data-dir`。

7. **网页上场的操作（不改规则）。** `/play` 并入全屏游戏画面的"我自己上"模式。点远处地面时，浏览器在"窗口内的物件 ∪ 自己的记忆地图"上做四连通寻路：可走的是地面、开着的门、完工的马桶；墙、关着的门、工地、柱子、没见过的格子、窗口内别人站的格子都不可走。找到就一次提交 `move` 路径串，找不到（或超过 200 步）就提示"走不到"、不提交。服务端仍每 tick 走一格、被挡即停（§4.3），不替网页寻路。方向键/WASD 一次一格保留。上场模式下画面只由 `GET /api/play/state` 与静态的 `/api/terrain`、`/api/worlds` 生成，不连观战数据流（SSE、`/api/projection`），9×9 之外画成暗的记忆区；没见过的荒野格按静态地形画成林子。§18 第 5 条的数据面不变。

- **为什么**：3D 画面里厕所是整间 3×3 棚屋，四角立柱；两间厕所共用墙或四角空着画不出来。

- **未改动的部分**：§9 全部数值、围合判定、门、防御（除柱子格）、计分。
