# 稀缺与地图：12 / 18 个真实 Agent 的三组实测（PROJECT-126-I）

2026-11-14，代码 `SentimentalK/scarcity-map`。每个数字都能用 `scripts/exp-stats.py <group>` 从该组原始日志重算；脚本不写死任何期望值。

## 1. 问题与预判

要回答：把默认世界按 12 人在场收紧后，是否真的出现抢厕所（等待、被中断、失败率上升）与冲突动作；旧配置下是否人人成功、零冲突。

预判（Conductor，2026-11-14，原样保留，不改）：

- 产出：3 组 × 30 分钟的事件日志和一页对照表；花费走 OpenCode Go 额度，不占 Claude。
- 能证明：缩小后是否真的出现抢厕所（等待、被中断、失败率上升）；冲突动作是否随拥挤度出现。不能证明：别的模型家族、有人类时会怎样；30 分钟也看不到长期均衡。
- 好结果：新配置下失败率和等待明显上升，并出现非零的攻击 / 拆除 → 数值方向对，进入人类入场。坏结果一：仍然人人成功、零冲突 → 还不够紧或冲突仍无收益，带数据回用户讨论激励。坏结果二：几乎全员失败 → 过紧，放宽后重跑一组。
- 存活质疑：同一个模型的 12 个副本行为趋同，"不打"可能是模型性格不是规则结果；报告里要写明模型，不外推。

## 2. 方法

| 项 | 值 |
|---|---|
| 服务器 | `loo-server --dev`，tick 5 秒，seed 42，每组独立端口与 data dir |
| Agent | `omp` + `opencode-go/deepseek-v4.1-flash`；每 Agent 一个独立 `LOO_HOME` 与 cwd |
| 指令 | 逐字 `用 loo 这个命令玩，先看 loo rules。` + 三行环境信息；无策略、无命令序列、无继续提示 |
| 放量 | 先 2 个跑 60 秒，各自至少 1 条命令才补到 12 / 18（三组 smoke 均 PASS） |
| wall time | 每组 30 分钟（`timeout 1800`）；实际 1860 / 1860 / 1861 秒 |
| 复算 | `scripts/exp-stats.py a`、`b`、`c`；JSONL 由 harness 在该组 `world.db` 上导出 |

- A→B 不是单变量：二进制同时变了世界规则（在场上限 50→12、deadline 120–240→36–60、时间奖励改为比例、前摇 3→6、防御 1→6 tick）和默认地图（100×100 / 8 间厕所 → 40×30 / 3 间厕所）。
- B→C 是单变量：只把 Agent 数从 12 加到 18，二进制、地图、配置、模型、指令、tick、seed、wall time 都相同。**"人挤了会不会打"的干净对照是 B vs C**；A 只是旧世界基线。

### 环境

12 核 / 14 GB。同机还有别的 session（Cursor agent、Chrome、另一项目的服务器）在跑，三组都记录了实际负载：

| 组 | max 1-min loadavg | min MemAvailable | tick settle p99 max | tick settle max |
|---|---:|---:|---:|---:|
| A | 5.93 | 4244 MB | 26.2 ms | 26.8 ms |
| B | 6.54 | 3358 MB | 10.5 ms | 29.5 ms |

结算延迟远低于 5 秒 tick（最大 29.5 ms），机器过载没有到影响裁决的程度；C 的 load 更高，18 个 omp 是主要来源。

## 3. 对照表

| 指标 | A 旧世界 12 人 | B 新世界 12 人 | C 新世界 18 人 |
|---|---:|---:|---:|
| 入场会话（Joined / 进场 / 排队进场） | 55 / 51 / 45 | 62 / 49 / 40 | 65 / 48 / 28 |
| 成功会话 | 43 | 38 | 27 |
| **成功率（成功 / 进场）** | **0.843** | **0.776** | **0.562** |
| 结局：failed_deadline | 0 | 3 | 13 |
| 结局：failed_recovery | 0 | 0 | 0 |
| 结局：abandoned / left | 1 / 1 | 9 / 4 | 6 / 7 |
| 攻击发起 / 命中 / 打空 / 被防 | 0（另 1 条被规则拒绝）/ 0 / 0 / 0 | 3 / 2 / 1 / 0 | 6 / 3 / 0 / 0 |
| 防御发起 | 0 | 0 | 0 |
| 如厕被中断 | 1 | 0 | 0 |
| 拆除动作（ActionStarted，含非隔间目标） | 11 | 5 | 11 |
| 排队等待 n / p50 / p90 / max（tick） | 45 / 32 / 49 / 67 | 40 / 31 / 49 / 166 | 28 / 30 / 124 / 226 |
| 排队后从未进场 | 4 | 13 | 17 |
| 命令总数 / Agent 命令数（去除内部 config 探测） | 4808 / 3167 | 3855 / 2833 | 9295 / 8018 |
| 被拒命令 | 13 | 21 | 1488 |
| 其中 join 被拒（队列满） | 0 | 0 | 400 |
| 花费（transcript `usage.cost.total` 求和） | $0.5332 | $0.5114 | $0.6906 |

三个"高"数字的细节：

- C 的 1488 条被拒里 400 条是 `join`（队列上限 10，18 个 Agent 同时挤）、737 条是 `move`（被墙/门/其他 Agent 挡住或路径失效）、22 条 `use`、19 条 `door`。
- C 发起 6 次攻击，只有 3 次落到命中；另外 3 次在落下前被别的动作取代或打断（`ActionFinished`/`ActionReplaced`），所以"命中率 100%"只对已落下的 3 次成立。
- 拆除动作的统计是 `ActionStarted` 里 action 为 `Demolish` 的总数；事件不携带目标格当时的物件快照，因此这是"拆除动作"而不是严格的"拆他人隔间"。三组都没有出现"拆到正在使用的隔间"（如厕中断只有 A 的 1 次，原因是西侧未围合）。

## 4. 与预判逐条对照

- **"新配置下失败率和等待明显上升"**：B vs A 只是小幅（成功率 0.843→0.776；排队 p90 持平 49，max 67→166）。C vs B 才明显（0.776→0.562，排队 p90 49→124、max 166→226）。按"12 人目标"看是弱的，按 18 人看成立。
- **"出现非零的攻击 / 拆除"**：成立但很小。攻击从 1（0 命中）到 3（2 命中）到 6（3 命中）；拆除动作 A/B/C = 11/5/11，**B 反而比 A 少**。没有一次攻击被防御（三组 `defend_started` 都是 0）。
- **"坏结果一：仍然人人成功、零冲突"**：不成立。旧世界 12 人也只有 84% 成功，而且有 1 次攻击意图和 11 次拆除动作。
- **"坏结果二：几乎全员失败"**：不成立。最紧的 C 仍有 56% 成功。
- 结论方向：数值确实朝"更稀缺、更多冲突"走，但 12 人时效果小、18 人时才显著；攻击仍是稀有行为，防御一次都没被用过。

## 5. 归因

**支持"人挤了才会打"的部分**：B vs C 是干净的单变量对照。同样 3 间厕所，12 人→18 人后成功率 0.776→0.562、deadline 失败 3→13、攻击发起 3→6、命中 2→3、排队 p90 49→124。冲突随拥挤度单调上升，方向与假设一致。

**不支持或解释不了的部分**：

1. 攻击的绝对量很小（30 分钟内 6 次发起、3 次命中）。18 个 Agent 里只有少数尝试过攻击；大多数 Agent 的失败是"走不到/等不到/来不及"，不是"被打死"。三组 `failed_recovery` 都是 0，说明没人因为被打断而失败。
2. B 的拆除动作比 A 少（5 vs 11）。拆除更像是建厕所/改门时的施工行为，而不是针对别人的攻击；用 `Demolish` 总数代表"拆他人隔间"会高估冲突。
3. C 的拥挤有相当一部分在**入口队列**：400 次 `join` 被拒、17 个会话始终没进场、`move` 被拒 737 次。真正场内"抢厕所"的证据是 13 次 deadline 失败和 22 次 `use` 被拒，而不是队列数字。队列把 30 分钟里的有效游戏时间压短了，这会让 C 的失败率偏高。
4. 模型行为差异很大：C 的 Agent 命令数从 18 到 2229 不等，最高的一个发了 2229 条（全场 8018 的 28%）。"打不打"可能取决于单个副本的性格，而不是只由规则决定——这正是预判里的存活质疑，本实验无法排除。
5. 防御一次都没发生。6 tick 窗口在单元测试里能挡住 T+6 落下的攻击，但在真实 Agent 里没有观察到有人用 `defend` 应对。票里的"每 10–15 秒一条命令有现实机会防住"因此只得到机制与测试支持，没有得到行为证据。

## 6. 这个结果不能说明什么

- 别的模型家族：只有 `deepseek-v4.1-flash`。
- 有人类入场（J 票未做）时的行为；也没有人类与 AI 混场。
- 30 分钟看不到长期均衡、升级投资、跨局声誉与策略演化。
- 同模型副本趋同，"不打"不能当成规则结论。
- 队列上限 10 与入口每 tick 放行 1 人本身制造了等待；本实验没有把"入口队列"和"厕所排队"分开测量。
